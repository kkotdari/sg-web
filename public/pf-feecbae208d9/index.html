01
Why · Needs · Motivation

우리 클랜이 모일 곳이 필요했다

> prompt클랜원이 편하게 소통하며 참여도를 높일 수 있는 장을 마련.기술보다 먼저 정한 것 — 누구를 위해, 왜 만드는가.

대화는 흘러가 버리고, 경기 결과는 각자의 컴퓨터에 흩어지고, 어제 그 명경기는 말로만 남는다. STARGATE는 이 세 가지 아쉬움에서 출발했습니다. 기능 하나하나가 아래 세 목적 가운데 어디에 닿는지를 기준으로 골랐습니다.

01

편하게 소통하고, 더 많이 참여하는 장

클랜원 누구나 부담 없이 들어와 말을 걸 수 있어야 했다. 게시판(공지·일정·공략·잡담·질문), 게임마다 댓글·추천, 회원 @태그, 그리고 내가 언급되거나 내 경기에 반응이 오면 푸시 알림. 리그·일정·배치고사는 다 같이 참여할 계기를 만든다.

고민 · 클랜원은 개발자가 아니다. 그래서 리플레이 올리기는 업로더가 알아서, 알림 설정은 켜고 끄기 하나로.
02

역사와 추억의 아카이브

함께한 경기는 클랜의 역사다. 리플레이가 올라오면 결과·참가자·맵·시작 위치가 자동으로 기록되고, 리그 대진과 명예의 전당이 시즌을 넘어 남는다. 몇 년 뒤에도 그날의 경기를 그대로 다시 재생할 수 있다.

고민 · 영원히 남겨야 할 것과 지워도 되는 것은 다르다. 그래서 무거운 재생 데이터와 가벼운 통계 데이터의 수명을 갈랐다(04장).
03

게임 모임다운 고급 데이터

게임 모임이라면 "누가 이겼나"보다 한 걸음 더 들어가고 싶다. 원작 엔진으로 경기를 다시 돌려 분당 일꾼·자원·데미지·우세도, "질럿 러시를 한 경기" 같은 전술 검색, 그리고 경기를 직접 다시 보는 3D 재생과 자동 중계.

고민 · 틀린 데이터는 믿음을 잃는다. 그래서 원작과 한 프레임씩 대조했다(05장) — 552,929프레임, 어긋난 난수 0.

Overview

클랜의 모든 경기가 기록되고, 다시 재생되는 곳

> prompt모든 건물 우클릭 대상으로! 원작이 그럼.기준은 늘 하나였다 — 원작이 어떻게 하는가.

◆무엇을 하는 서비스인가

  • 업로더(데스크톱 앱)가 리플레이를 올리면 경기 결과·참가자·맵·시작 위치가 자동 등록
  • 서버가 리플레이를 원작 엔진(OpenBW)으로 다시 돌려 유닛 궤적·데미지·자원 같은 참값을 뽑음
  • 참값으로 통계·래더·검색·우세도 그래프를 만들고, 웹에서 3D 재생·자동 중계
  • 리그(대진표·세트), 배치고사(라운드로빈 점수), 일정(노션형 문서), 외부 공유까지

API · Performance

왕복은 줄이고, 계약은 지킨다

> prompt그리고 게임 목록 조회 시 배치맵도 같이 담겨서 오게. 한 번에.목록 → 맵 두 번 왕복을 한 번으로. 이미 받은 맵은 클라이언트가 알려 서버가 뺀다.

⇄이렇게 설계했다

  • 한 번의 응답: 활동 목록에 그 쪽 경기의 맵 격자를 싣고 knownMap으로 중복 제외 · 통계는 7개월 추이를 한 응답에
  • 하위 호환 배포: 새 웹 ↔ 옛 서버, 옛 웹 ↔ 새 서버 어느 순서로 올라가도 동작하게 필드를 덧붙이는 방식만 사용
  • DB 변경은 SQL 파일로 저장소에 남기고 운영자가 직접 실행 → 그다음 서버 배포 (자격증명은 절대 주고받지 않음)
  • 입력 검증: 시작 위치처럼 바깥에서 오는 값은 검증기에서 반올림·범위 밖은 "모름"으로
  • 권한·공유: JWT + 리프레시, 역할 코드, 외부 공유 목록은 별도 패스 헤더 · 손님 모드 가명
  • 테스트 404개: httpx 비동기 클라이언트로 엔드포인트 단위 시나리오 · 린트는 기존 대비 새 경고 0을 관문으로

Reusability · Extensibility · Maintainability

한 곳만 고치면 전부 바뀌게

> prompt활동과 일정, 너나와, 리그, 게임 목록과 상세 등 모두 컴포넌트 분리.기능이 늘수록 경계를 먼저 다시 그었다.

R재사용성

  • 재생기를 별도 라이브러리(scplay)로 떼고, 앱은 미리 빌드된 dist 커밋만 받는다 — 배포마다 40초 빌드 제거
  • 라이브러리는 앱의 API 주소를 모른다: setReplayMapFetcher 같은 주입으로만 연결(의존 역전)
  • 로스터 한 벌(GameRowNames)을 목록·PC 표·재분석·삭제함·외부 공유·리그 세트 6곳이 공유
  • 전술 색인 함수 하나를 재생기 검색과 서버 색인이 함께 쓴다

E확장성

  • 경기 유형은 GAME_TYPES 명세 표 한 곳(팀전 여부·래더·순위 구간) — 새 유형은 한 줄
  • 대진표는 경로 문자열("", "a", "b"…)로 표현해 임의 크기의 트리와 부전승을 같은 코드로
  • 참값 트랙은 판 번호(9→13)로 버전을 매겨 옛 데이터도 그대로 읽는다
  • 기기 프로필 DEV9 표 하나로 폰·PC 성능 단을 조정

M유지보수

대화로 여러 번에 나누어 건넨 요청을, 의도가 드러나도록 하나의 작업 지시서로 정리했습니다.

> promptportfolio.brief
  1. 자료 — 검증 일지(원판과 같아지기)와 그동안의 작업 기록·커밋·대화를 전부 읽고, 과장 없이 사실과 수치로만 쓴다.
  2. 분량과 배포 — 한 번에 읽히는 적당한 분량으로 만들어 sg-web에 배포한다. 메뉴·링크 없이 주소를 아는 사람만 들어오게 하고, 검색엔진에도 노출하지 않는다.
  3. 테마 — 밝고 미래적이되, 스타크래프트의 정체성(사이오닉 블루, 홀로그램 HUD, 종족 색)이 느껴지게.
  4. 주인공 — 백엔드 개발자로서의 강점: 데이터 파이프라인, 데이터 수명 설계, API 계약, 검증과 테스트.
  5. 태도 — 치열한 고민과 노력, 끈기, 그리고 AI와의 협업 방식을 이야기의 중심에 둔다.
  6. 설계 관점 — 재사용성 · 확장성 · 유지보수를 구체적인 사례로 보여준다.
  7. 리그 · 일정 화면 — 그 특징과 함께, 어느 클럽에서나 쓸 수 있는 보편성과 쓰는 사람의 편의성을 강조한다.
  8. 시각자료 — 말보다 그림이 많게. 홈페이지, 3D 모델 도록, 재생기를 직접 캡처해 넣는다.
  9. 목소리 — 내가 실제로 건넨 프롬프트 중 멋진 것을 골라 맨 위에 걸고, 제목은 멋지게. 각 장의 시작도 프롬프트로 연다.
  10. 앱 — 아이폰 PWA · 안드로이드 앱 · 푸시 알림 같은 앱 관련 내용도 담는다.
  11. 동기 — 개발적인 것만 강조하지 말고 니즈 · 동기 · 고민을. 처음에 왜 이 앱을 만들었는지 — 클랜원이 편하게 소통하며 참여도를 높일 장, 역사와 추억의 아카이브, 게임 모임다운 고급 데이터.
  12. 접근법의 전환 — 이미지를 미리 구워 내려받는 방식으로 바꿔 성능 한계를 넘고, 그 덕에 내부 그림자 · 선명도 · 대비 같은 모델 품질을 올릴 수 있게 된 과정.
  13. 맺음 — 이 지시서 자체를 마지막에 남겨, 이 페이지가 어떻게 만들어졌는지도 보여준다.
